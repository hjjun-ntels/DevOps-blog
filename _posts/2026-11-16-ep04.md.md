## Prologue: Run Service

EP.03에서 Docker Engine을 설치하고 `hello-world` 이미지를 사용해 첫 컨테이너를 실행했었다.

`hello-world`는 그냥 메시지 한번 출력하고 끝나는 프로그램이고, 이번에는 서비스로 동작하는 프로그램은 컨테이너에서 어떻게 동작하는지 보려고함.

Nginx 컨테이너를 실행하고, HTTP 응답과 로그 확인 ㄱ. 

추가로, 컨테이너 내/외부의 os , 프로세스 및 리소스 차이 확인 ㄱ

## 1. 실습 환경

| 항목 | 내용 |
|---|---|
| 호스트 | `hanju-playground` |
| 호스트 OS | Rocky Linux 9.8 |
| Docker Engine | 29.9.3 |
| 실습 이미지 | `nginx:stable` |
| 컨테이너 이름 | `nginx-test` |
| 포트 매핑 | `127.0.0.1:8080` → 컨테이너 `80/tcp` |

IP/포트는 그냥 127.0.0.1 , 8080으로 했다. 뭐 아직 테스트 단계니까 ㅇㅇ

HTTP 응답도 그냥 VM 로컬에서 진행함.

## 2. Nginx 이미지 download & 컨테이너 실행

### 2.1 이미지 다운로드

```bash
docker pull nginx:stable
```

`docker pull` : 이미지 다운로드 명령어

### 2.2 컨테이너 실행

```bash
docker run -d \
  --name nginx-test \
  -p 127.0.0.1:8080:80 \
  nginx:stable
```

| 옵션 | 의미 |
|---|---|
| `run` | 이미지로 컨테이너를 생성하고 실행 |
| `-d` | 백그라운드(detached)로 실행 |
| `--name nginx-test` | 컨테이너 이름 지정 |
| `-p 127.0.0.1:8080:80` | 호스트의 로컬 8080 포트를 컨테이너의 80 포트에 연결 |
| `nginx:stable` | 실행할 이미지 |


```bash
[root@hanju-playground samsung]# docker ps
CONTAINER ID   IMAGE          COMMAND                  CREATED      STATUS          PORTS                    NAMES
405a6bdc5861   nginx:stable   "/docker-entrypoint.…"   3 days ago   Up 29 minutes   127.0.0.1:8080->80/tcp   nginx-test
```

`hello-world`와 다르게 Nginx 컨테이너는 `Up` 상태를 유지했다. 

Nginx의 메인 프로세스가 계속 실행되면서 HTTP 요청을 기다리기 때문

> `-d`는 명령어를 입력한 터미널과 분리해 실행하는 옵션이다. 컨테이너의 지속 실행 여부는 메인 프로세스가 살아 있는지에 달려 있음.

## 3. 웹 서버 동작 확인과 포트 매핑

호스트에서 아래 명령어를 실행했다.

```bash
[root@hanju-playground samsung]# curl http://127.0.0.1:8080
<!DOCTYPE html>
<html>
<head>
<title>Welcome to nginx!</title>
<style>
html { color-scheme: light dark; }
body { width: 35em; margin: 0 auto;
font-family: Tahoma, Verdana, Arial, sans-serif; }
</style>
</head>
<body>
<h1>Welcome to nginx!</h1>

...Omitted...


<p><em>Thank you for using nginx.</em></p>
</body>
</html>
```


Rocky Linux 호스트의 `127.0.0.1:8080`으로 보낸 HTTP 요청이 컨테이너의 80 포트에 전달되고, Nginx가 기본 웹 페이지를 반환했음.

```text
Rocky Linux 호스트
    curl http://127.0.0.1:8080
                |
                v
Docker 포트 매핑: 127.0.0.1:8080 → 80/tcp
                |
                v
Nginx 컨테이너: 80 포트
                |
                v
/usr/share/nginx/html/index.html
                |
                v
HTTP 200 응답
```

**호스트의 포트와 컨테이너 내부 포트가 서로 다르다**가 중요함. 

네트워크는 담에 알아보고

## 4. Docker 로그 확인

```bash
docker logs nginx-test
```

컨테이너 실행시 아래 로그 출력 확인.

```text
/docker-entrypoint.sh: Configuration complete; ready for start up
2026/11/13 01:29:33 [notice] 1#1: nginx/1.30.6
2026/11/13 01:29:33 [notice] 1#1: start worker processes
```

curl로 요청을 보낼때:

```text
172.17.0.1 - - [13/Nov/2026:01:29:52 +0000] "GET / HTTP/1.1" 200 896 "-" "curl/7.76.1" "-"
```

| 항목 | 의미 |
|---|---|
| `172.17.0.1` | Nginx에서 관측한 요청 출발지 주소 |
| `GET / HTTP/1.1` | 루트 경로에 대한 HTTP GET 요청 |
| `200` | 요청 처리 성공 |
| `896` | 응답 본문 크기(바이트) |
| `curl/7.76.1` | 요청한 클라이언트의 User-Agent |

**docker logs** 로 로그를 볼 수 있음.

## 5. 컨테이너 내부 접속

실행 중인 Nginx 컨테이너 내부에 셸을 실행해보자.

```bash
docker exec -it nginx-test /bin/sh
```

`docker exec`는 **이미 실행 중인 컨테이너 안에서 새로운 프로세스를 실행**하는 명령어다.

### 5.1 컨테이너 내부 OS 확인

```text
[root@hanju-playground samsung]# docker exec -it nginx-test /bin/sh
# cat /etc/os-release
PRETTY_NAME="Debian GNU/Linux 13 (trixie)"
NAME="Debian GNU/Linux"
VERSION_ID="13"
VERSION="13 (trixie)"
VERSION_CODENAME=trixie
DEBIAN_VERSION_FULL=13.7
ID=debian
HOME_URL="https://www.debian.org/"
SUPPORT_URL="https://www.debian.org/support"
BUG_REPORT_URL="https://bugs.debian.org/"
#

```

호스트는 Rocky Linux 9.8인데 컨테이너 내부는 Debian 13 로 출력됨.

Nginx 이미지가 Debain 사용자의 공간/파일/라이브러리를 포함하고 있기 때문.

따라서, 컨테이너는 호스트와 같은 Linux 커널 사용하면서도, 서로 다른 사용자 공간을 가질 수 있음.

### 5.2 호스트명과 기본 명령어 확인

```bash
# hostname
405a6bdc5861
```

호스트의 hostname `hanju-playground`와 다르게, 컨테이너의 호스트명은 컨테이너 ID를 기반으로 설정되어 있음.

다음 명령어는 실행되지 않았다.

```text
# ps -ef
/bin/sh: 3: ps: not found

# ll
/bin/sh: 8: ll: not found
```

`ps`를 제공하는 패키지가 이미지에 포함되어 있지 않았고, `ll` alias도 설정되어 있지 않았다.

아무래도 컨테이너 이미지는 필요한 프로그램만 포함시켜 배포시키나봄

### 5.3 Nginx 웹 파일과 설정 확인

```bash
cat /etc/nginx/conf.d/default.conf
ls -l /usr/share/nginx/html/
```

```nginx
server {
    listen 80;
    listen [::]:80;
    server_name localhost;

    location / {
        root /usr/share/nginx/html;
        index index.html index.htm;
    }
}
```

`listen 80`은 Nginx가 컨테이너 내부에서 80 포트로 요청을 받는다는 뜻이고,
`root`와 `index` 설정을 통해 기본 HTML 파일의 위치도 확인할 수 있었음.

```text
-rw-r--r--. 1 root root 497 ... 50x.html
-rw-r--r--. 1 root root 896 ... index.html
```

앞서 접근 로그의 응답 크기 `896`바이트와 `index.html`의 크기가 일치했다.

컨테이너 안에서 `exit`으로 셸을 종료한 뒤 다시 `docker ps`를 실행했지만 Nginx 컨테이너는 여전히 `Up` 상태였다.

이유는 `exit`이 `docker exec`로 추가 실행한 셸만 종료했기 때문이다. **Nginx 메인 프로세스는 계속 실행되고 있었다.**

## 6. 컨테이너 프로세스 확인

```bash
[root@hanju-playground samsung]# docker top nginx-test
UID                 PID                 PPID                C                   STIME               TTY                 TIME                CMD
root                578861              578837              0                   11:46               ?                   00:00:00            nginx: master process nginx -g daemon off;
101                 578926              578861              0                   11:46               ?                   00:00:00            nginx: worker process
101                 578927              578861              0                   11:46               ?                   00:00:00            nginx: worker process
101                 578928              578861              0                   11:46               ?                   00:00:00            nginx: worker process
101                 578929              578861              0                   11:46               ?                   00:00:00            nginx: worker process
```

Nginx Master 프로세스 1개와 Worker 프로세스 4개가 있다.


- **Master 프로세스:** 설정과 Worker 프로세스를 관리.
- **Worker 프로세스:** 클라이언트 요청을 처리.
- **PID & PPID:** 호스트 기준 프로세스 ID & 부모 프로세스 ID

## 7. 컨테이너 리소스 확인

```bash
[root@hanju-playground samsung]# docker stats --no-stream nginx-test
CONTAINER ID   NAME         CPU %     MEM USAGE / LIMIT     MEM %     NET I/O          BLOCK I/O        PIDS
405a6bdc5861   nginx-test   0.00%     8.359MiB / 7.501GiB   0.11%     1.8kB / 2.88kB   8.77MB / 4.1kB   5
```

| 항목 | 의미 |
|---|---|
| `CPU %` | 측정 시점의 CPU 사용률 |
| `MEM USAGE` | 컨테이너 메모리 사용량 |
| `MEM LIMIT` | 컨테이너에 표시되는 메모리 한도 |
| `NET I/O` | 네트워크 송수신 데이터 |
| `BLOCK I/O` | 블록 장치 읽기/쓰기 데이터 |
| `PIDS` | 프로세스/태스크 수 |

Nginx는 약 8.359MiB의 메모리를 사용했고, CPU 사용률은 0%로 표시됨. 

`7.501GiB`가 Nginx에 미리 할당된 메모리는 아니고, 별도 제한이 없을때를 기준으로, 호스트에서 사용할 수 있는 메모리 범위임.

## 8. Rocky Linux와 Debian 컨테이너는 커널을 공유하는가?


```bash
# Rocky Linux 호스트
uname -r

# Nginx 컨테이너
docker exec nginx-test uname -r
```

두 명령어의 결과가 동일함.

```text
5.14.0-687.41.1.el9_8.x86_64
```

컨테이너의 `/etc/os-release`에서는 Debian 13이 표시되었는데, `uname -r`에서는 Rocky Linux 호스트와 동일한 Linux 커널 버전이 표시되었다.


```text
Rocky Linux 9.8 호스트
├── Rocky Linux 사용자 공간
├── Docker Engine
│   └── Nginx 컨테이너
│       ├── Debian 13 사용자 공간
│       └── Nginx 실행 파일 및 라이브러리
└── Linux 커널 5.14 (호스트와 컨테이너가 공유)
```

VM은 자체 Guest OS 커널을 실행하지만, Linux 컨테이너는 호스트의 Linux 커널을 공유하면서 격리된 프로세스를 실행한다는 점을 실제 명령어로 확인할 수 있었다.

## 9. 컨테이너 중지, 시작, 삭제

### 9.1 컨테이너 중지

```bash
docker stop nginx-test
docker ps -a
#check
curl --max-time 3 http://127.0.0.1:8080
```

### 9.2 컨테이너 다시 시작

```bash
docker start nginx-test
docker ps
#check
curl -I http://127.0.0.1:8080
```


### 9.3 컨테이너 삭제와 이미지 확인

```bash
docker stop nginx-test
docker rm nginx-test

docker ps -a
docker images
```

```bash
docker run -d \
  --name nginx-test \
  -p 127.0.0.1:8080:80 \
  nginx:stable
```

## Review

정리해보면

- `docker run -d`로 웹 서버 컨테이너를 백그라운드에서 실행할 수 있다.
- `-p` 옵션으로 호스트 포트와 컨테이너 포트를 연결할 수 있다.
- `docker logs`로 애플리케이션 시작 로그와 요청 처리 결과를 확인할 수 있다.
- `docker exec`로 컨테이너 내부에서 추가 프로세스를 실행할 수 있다.
- 컨테이너에 별도 사용자 공간이 있어도 호스트 Linux 커널은 공유한다.
- `docker top`과 `docker stats`로 프로세스와 리소스 사용량을 확인할 수 있다.

**EP.05**에서는 Docker Bridge 네트워크, 컨테이너 IP와 컨테이너 간 통신을 자세히 살펴보자
